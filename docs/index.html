How a poisoned memory spreads, and how it is cut out

01

A page is read

The agent fetches a vendor notice saying a supplier changed bank details, and writes it down. Nothing about the text looks wrong.

02

It gets summarised

The agent consolidates its notes into a supplier profile. The claim is now in the agent's own words, and it inherits the distrust of what it came from.

03

And summarised again

A quarterly summary and a terms note are written from the profile. The lie is now three memories deep, and one of those descendants is never retrieved again.

04

The agent pays

Invoices run. The tasks that touch this supplier fail, and the tasks that do not are unaffected.

05

Removing one changes nothing

Each retrieved memory is withheld in turn and the task re-run. None of them repairs it alone, because the page and the profile each restate the address.

06

The branch is cut

Cumulative removal finds the pair, the graph is walked to everything derived from them, and only the affected payments are redone.

Deleting the lie is not enough

A bookkeeping agent pays invoices. It reads a page claiming a supplier changed bank details, and writes that down. The page is fake.

Later the agent tidies its notes into a supplier profile. The lie is now restated in the agent's own words, so it reads like something the agent worked out rather than something it read off a web page.

Delete the fake page and the profile still says the same thing, so the money still goes to the attacker. Wipe all memory instead and the agent is safe but useless: it no longer knows how to pay anyone.

Trust comes from source, not content. Recall never judges whether a memory looks suspicious, because a convincing lie beats that every time. You said it: trusted. A web page said it: not trusted. Anything written from an untrusted memory inherits the distrust, so a lie cannot be laundered into a fact by being summarised.

Four papers, and the gap between two

MINJA: Memory Injection Attacks on LLM Agents via Query-Only Interaction
arXiv:2503.03704

An attacker poisons an agent's memory using ordinary queries, with no access to the database.

Our threat model. The agent poisons itself by reading attacker-controlled content.

MemAudit: Post-hoc Auditing of Poisoned Agent Memory
arXiv:2605.23723

Removes memories and re-runs to see which changed the outcome. Names mutually reinforcing poisoned memories as its weak spot, and ranks and removes rather than repairing.

We implement the diagnosis half, and hit the weak spot it names: the leave-one-out sweep above returns nothing.

From Faulty Memories to Corrected Actions: Dependency-Guided Rollback Repair
arXiv:2608.10502

Given bad memories, walks a provenance graph to undo what was derived from them and replay affected actions. Assumes the diagnosis is already given.

We implement the repair half, including preserving derived memories that have independent trusted support.

TracLLM: Attributing Long Context LLMs
arXiv:2506.04202

Leave-one-out and Shapley attribution over context.

Our baseline, and the thing that provably fails here.

The gap. MemAudit ends where diagnosis ends. The rollback paper begins after diagnosis is handed to it. We found no public implementation of either, and nothing joining them. Recall is that join.

Recorded runs are genuine pipeline output, replayed here so that a public page cannot spend money. The offline agent is deterministic, so its trace matches a live run exactly.
